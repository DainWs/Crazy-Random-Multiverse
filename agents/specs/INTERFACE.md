# Interface behavior

How the interface behaves. Its appearance is in `../VIEW-SPECS.md`.

## Navigation

- **UI-1** The flow is: main menu → create a party, party list or join by code → party → loading → game → result → party.
- **UI-2** All texts are in Spanish and prepared to be translated. A text key without a translation in the client is shown as the key itself. **[Post-MVP]** English and dynamic localization.
- **UI-17** The screen shown follows the user state (`CON-23`): no party → main menu; in a party → party screen; loading → loading; game in progress → game, after the load of `LOAD-6` if it applies. A game that ends keeps the game screen, with the result over the board (`WIN-4`), until the server removes it (`WIN-5`). One that ended while the client was away takes it to the party (`CON-23`). The client waits for `user:synced` before choosing one, and changes screen whenever the state changes afterwards. It keeps the game state from the first event of the game on (`GAME_CREATED`), although the screen only changes with `GAME_LOADING`, whatever scene is active (`LOAD-6`), and drops it when the user no longer has a game.

## Game

- **UI-3** The interface shows whose turn it is and the current round, from the board being shown, not from the latest state received (`CON-12`, `VIEW-20`).
- **UI-4** The interface disables gameplay when it is not the player's turn, while the settings screen or the help panel is open (`UI-33`, `UI-34`), while an action is pending, while animations are still playing (`CON-12`), for a spectator and after the game ends. Waiting for the animations keeps what is shown in step with the state: the board of each event is drawn when the animations of the earlier events end, from the state that event carries.
- **UI-5** The interface disables what the state already shows to be invalid, highlights the valid slots of a dragged card (`VIEW-32`), and shows whether a card is a valid target of an attack when the pointer is over it (`VIEW-4`). It works them out from the board it holds: an attack from `attackAvailable` and `targetable` (`CON-15`), and a placement, a move or an equipment, which the contract does not flag, with `BOARD-5`, `BOARD-7` and `EQUIP-3`. The server validates each action again (`TURN-6`).
- **UI-6** While the server answers, a dropped card is shown where it was dropped and, in a swap, the other warrior is shown in the slot the card left (`BOARD-7`). If the server rejects the action, the cards go back to where they were and a brief message explains the reason, based on the error key. If it accepts it, they stay there until its event is applied (`HAND-2`). A 500, or any other status that is neither 2xx nor 400 (`CON-18`), and a request without response (`UI-24`) are shown the same way, with the client's own keys `exception.unexpected` and `exception.server_unreachable`, which the server never sends, and the card goes back too. The action may still have been applied: then its events place the card again (`CON-17`).
- **UI-25** When the player drops a card where the interface does not allow it (`UI-4`, `UI-5`), nothing is sent to the server: the card goes back to where it was and a brief message says why, as in `UI-6`. The reasons are that it is not their turn, that the slot or the target is not valid, that the card cannot be moved, or that no slot can take it. The attack by clicks shows no message: what each click does while attacking is in `VIEW-4`.
- **UI-7** Rival hands are not shown (`HAND-3`). **[Post-MVP]** They are shown as backs (`VIEW-3`).
- **UI-8** A spectator or eliminated player sees the board with all interaction disabled, except a button to leave (`SPEC-3`).
- **UI-15** Surrendering asks for confirmation (`ELIM-2`), and so do leaving the party (`PARTY-6`), kicking a member (`UI-23`) and leaving the game as a spectator (`SPEC-3`).

## Effects and settings

- **UI-26** Every animation and visual effect of the interface is either essential or non-essential, and the rule of each one says which. An essential effect shows information the player needs: a change of the game state, or the state of their own interaction, such as which card is selected or whether a card can be attacked. A non-essential effect only decorates: without it the game is fully readable and nothing the player needs is lost.
- **UI-27** **[Post-MVP]** The settings screen (`UI-33`) gets two more options, for the effects: the graphics quality, normal or low, and reduced motion, on or off. They are the preferences of that player only, like the skins (`FX-12`), and are not part of the game state nor of the contract. They are kept in the browser of the player, on that device, between visits: not on the server, and they do not follow the player to another device. They start at normal quality. Reduced motion starts on when the operating system asks for reduced motion and the player has never changed the option; once the player changes it, their choice is kept and the operating system is no longer followed.
- **UI-28** **[Post-MVP]** With low quality, non-essential effects do not happen, and essential effects play as in normal quality. No essential effect has a low quality version: they only change the size, the place or the opacity of what is on the screen, and what costs more (the shake, the flash, the freeze, the effects of `VISUAL-EFFECTS.md`) is non-essential. Decided by the product owner on 2026-11-17.
- **UI-29** **[Post-MVP]** With reduced motion, non-essential effects do not happen, and an essential effect neither moves nor changes its size:
  - What appears fades in, at its final place and size, in 150 ms, slowing down at the end.
  - What disappears fades out, at its place and size, in 150 ms, speeding up.
  - What travels or changes its size fades out at its start while it fades in at its end, in 150 ms, slow at both ends.
  - A fade, a frame, a count or a text that does not move plays as with reduced motion off.

  An essential effect whose rule writes its own reduced motion version plays that one instead. Decided by the product owner on 2026-11-17.
- **UI-30** The MVP has no settings for the effects: every effect plays as in normal quality and without reduced motion, and the reduced motion option of the operating system is not followed. The one exception are the pulses of `VIEW-17`, `VIEW-20` and `VIEW-38`, which do not pulse when the operating system asks for reduced motion. The parameter of `UI-31` is the other exception. The only option of the settings screen in the MVP is the camera of `UI-33`. The interface is built so that adding the options of `UI-27` only adds them to that screen, without changing the rules of the effects.
- **UI-31** The accessible mode is turned on with the parameter `accessible=1` in the address of the page, read when the page loads. Without it, or with any other value, the game is the base game: as before Phase 11.1, plus the minimum size of the texts, the panel of the round and the turn, and the keyboard. The mode turns on, all together, the extra signals of the marks of the board (`VIEW-39`), the colors and the near black edge of the marks of `VIEW-40`, the red mark of the source slot that stays while a card is dragged (`VIEW-32`), and the darkened background around the table (`VIEW-45`). The minimum size of the texts (`VIEW-41`), the panel of the round and the turn (`VIEW-40`) and the keyboard (`UI-32`, `VIEW-42`, with the focus of the notices) are part of the base game, also without the parameter. The parameter `extraMarks=1` turns on only the extra signals. Neither is kept between visits, part of the game state or of the contract, and neither is an option of the settings screen (`UI-33`). Decided by the product owner on 2026-11-18, and on 2026-11-19 for `accessible`, so that nothing that makes the game accessible changes the look of the base game.
- **UI-32** The keyboard, in the base game and in the accessible mode (`UI-31`). Decided by the product owner on 2026-11-19, who asked on 2026-11-19 that it stays in the base game although it is also an accessibility feature.
  - **End the turn.** The Space key ends the turn as the button does (`UI-4`): nothing happens while the button is disabled, for a spectator, while the confirmation dialog is open and while the notice of `UI-9` covers the interface. Holding the key down does not repeat it, and its default action in the browser (scrolling the page) does not happen on the game screen.
  - **Confirmation dialog** (`UI-15`). When it opens, the focus is on its "No" button. Tab, Shift+Tab, the left arrow and the right arrow move the focus between "No" and "Sí" and stay inside the dialog. Enter presses the button with the focus, and Escape presses "No" whichever button has the focus. No other key does anything while it is open. The focus is drawn as `VIEW-42` says.
  - **Notices** (`UI-9`, `UI-10`, `UI-24`). When one opens, the focus goes to its first button. A notice with no button, such as the one of `UI-9`, takes the focus itself. While it is open, Tab and Shift+Tab only move the focus inside it, and the focus never goes to what is under it.
- **UI-33** The settings screen has one option in the MVP, the camera of the board (`VIEW-57`): "Cenital" or "Inclinada", one of the two chosen, "Cenital" the first time. The change applies at once. The choice is a preference of that player only and follows the storage of `UI-27`: kept in the browser of the player, on that device, between visits, and not part of the game state nor of the contract. A choice kept that is not one of the two is read as "Cenital". The screen is opened from a button in the top right corner of the main menu and of the game screen. It is a panel over the screen that disables gameplay while it is open (`UI-4`), the Space key included (`UI-32`), and it closes with the same button, with its own button, with Escape and with a click outside it. Decided by the product owner on 2026-11-20, who moved the settings screen out of Post-MVP for the values of the cards; on 2026-11-21 the values were removed and the camera took their place.

## Help

- **UI-34** The help panel is opened from a button with the sign "?" on the game screen only, next to the settings button (`UI-33`). The help and settings buttons are not gameplay, so a spectator uses them too (`UI-8`). The panel is over the screen and has two sections, the legend of the marks of the board (`VIEW-58`) and the summary of the rules (`UI-35`), and a button "Cerrar". It disables gameplay while it is open (`UI-4`), the Space key included (`UI-32`). It closes with the button that opened it, with "Cerrar", with Escape and with a click outside it, and it is closed when the client leaves the game screen. The settings screen and the help panel are never open at once: opening one closes the other. When it opens, the focus goes to "Cerrar", and Tab and Shift+Tab move the focus only inside it, as in the notices of `UI-32`. Decided by the product owner on 2026-11-22.
- **UI-35** The second section of the help panel, "Reglas", is this text, each paragraph with its title in bold, through the texts of `UI-2`. Approved by the product owner on 2026-11-22. It summarizes `SETUP-3`, `TURN-*`, `ROUND-3`, `BOARD-*`, `EQUIP-3`, `PROT-*`, `ELIM-*`, `SPEC-1` and `WIN-1`: a change in one of them checks this text.
  - **Objetivo.** Cada jugador tiene un líder a la vista de todos. Elimina a los líderes rivales antes de que eliminen al tuyo: gana el último jugador vivo.
  - **El turno.** Se juega por turnos, en un orden sorteado al empezar que no cambia. En tu turno puedes colocar, mover, equipar y atacar, sin límite de tiempo, y lo terminas con «Terminar turno». Al empezar cada ronda, todos reciben cartas nuevas.
  - **Colocar una carta.** Arrastra un guerrero de tu mano a un hueco libre de tu zona. La fila de atrás se llena antes que la de delante. Un guerrero recién colocado ataca a partir de tu siguiente turno. Durante tu turno puedes mover o intercambiar tus guerreros dentro de tu zona, pero el líder no se mueve. Para equipar una carta tuya del tablero, arrastra el equipo sobre ella.
  - **Atacar.** Haz clic en una carta tuya con marco cian y después en una carta rival que se pueda atacar. Cada carta ataca una vez por turno.
  - **Protección.** Mientras la fila delantera de una zona tenga cartas, su fila trasera no puede ser atacada. Mientras el líder tenga guerreros delante, ni puede ser atacado ni puede atacar.
  - **Eliminación.** Un jugador queda eliminado cuando muere su líder o cuando se rinde, cosa que solo puede hacer en su turno. Sus cartas salen del tablero y pasa a ver la partida como espectador.

## Connection and failures

- **UI-9** If the socket connection is lost, on any screen, a notice covers it and disables interaction while the client retries on its own, with no limit, also after the server closes the socket. A connection error makes the client check its session (`USER-8`). When the connection returns, the state is restored as in `CON-23`, from `GAME_SYNC` during a game.
- **UI-10** If the session has expired (`USER-8`), or a rejection during the load says that the game no longer exists or is not the user's (`UI-12`) and the user is not in a party, the client goes back to the main menu and explains what happened. An expired session starts as a new user (`USER-5`). A socket bound with no state before `user:synced` also takes the client to the main menu (`CON-23`), but without a message, whatever the reason, such as a kick while the user was away (`PARTY-12`).
- **UI-12** If the manifest, a `fixed` resource or `/ready` fails during the load (`LOAD-2`, `LOAD-6`), the client shows the failure and offers to retry, without confirming `/ready`. Retrying repeats only what failed. If the player closes the game, `LOAD-3` applies. A rejection with `exception.game.not_found` or `exception.access_denied.wrong_game` offers no retry: the client goes back to the party or, if the user is not in one, follows `UI-10`. `exception.user.not_found` follows `USER-8`.
- **UI-24** If a REST request gets no response outside the load (`UI-12`), because the server is down or the network is cut, a brief message says so where that screen shows its errors, and the client stays on it. At startup, the client shows the main menu with a notice that asks to reload the page. A lost socket connection follows `UI-9` instead. A request that reaches the server and is never answered has no time limit of the client, as in `LOAD-7`: the client keeps waiting until the page is reloaded, and a pending action keeps gameplay disabled meanwhile (`CON-19`, `UI-4`).
- **UI-21** The image of a card is downloaded the first time the card has to be shown, or during the load for the leaders of the game (`LOAD-2`), using the manifest (`CON-30`). Until it arrives, the card shows `card.unknown`, and the image replaces it when it does. A failed download keeps `card.unknown`, does not interrupt the game and is not attempted again until a card with that image enters the game: it is dealt to the hand, or the board gets one more copy of it. Drawing the board again does not count. A card the manifest does not list also keeps `card.unknown`.
- **UI-22** The loading screen shows the progress of the downloads and, after confirming `/ready`, a text saying that it is waiting for the other players (`LOAD-3`).

## Menu

- **UI-13** The name is edited from the main menu. The interface does not offer it inside a party, although the server accepts it (`USER-3`). A rejected name is shown as a message below the field, based on its key, as in `UI-18`, and the previous name is kept. The settings screen is opened from the main menu (`UI-33`).
- **UI-14** The party list is loaded when its screen opens and with a refresh button (`PARTY-4`). Each party shows its name and its members out of the capacity, and a full one shows the join button disabled (`PARTY-5`). A rejected join is shown as a brief message based on its key, as in `UI-18`, and the list is loaded again, because it was out of date.
- **UI-18** The main menu creates a party with one action, using the default capacity and the Classic mode (`PARTY-2`, `PARTY-3`), and joins one with a field for the party code. Any failure, of creating or of joining, is shown as a message below the field of the code, based on its key: a rejection (`CON-18`), such as `exception.party.not_found`, or `exception.request.malformed` for a code that cannot be read, the client's `exception.unexpected` for a 500 (`UI-6`), and the message of `UI-24` without a response. `exception.user.not_found` also follows `USER-8`.

## Party

- **UI-16** The party screen disables starting the game, kicking and the configuration while the party is locked (`PartyDto.locked`). Leaving stays enabled, because a spectator can leave at any moment (`SPEC-3`) and the client does not know who is one: it only learns of the lock through `party:info`, and it shows a locked party without the game state, after a socket is bound during the result (`CON-23`, `WIN-5`), or when `GAME_CANCELLED` arrives before the `party:info` that unlocks the party and the last one received was locked (`LOAD-5`). The server rejects the others with `exception.party.locked` (`PARTY-3`, `PARTY-6`, `PARTY-9`), shown as a brief message based on its key, as in `UI-18`.
- **UI-19** The party screen shows the name, the number of members out of the capacity, the members, with the owner first and marked and the others in the order they joined (`CON-38`), and the code with a button to copy it (`PARTY-5`, `PARTY-11`). Any member can leave from it (`PARTY-6`).
- **UI-20** Only the owner sees the start button. It is disabled while the party is locked (`UI-16`) or has fewer than 2 members (`PARTY-9`). A rejected start (`PARTY-9`, `DECK-4`) is shown as a brief message below the button, based on its key, as in `UI-18`.
- **UI-23** Only the owner sees the configuration controls: the capacity, from 2 to 10 (`PARTY-2`), the game mode selector, with Classic as its only option (`PARTY-3`, `SCOPE-3`), and a button to kick each member except themselves (`PARTY-6`). A rejection is shown as a brief message based on its key, as in `UI-18`.
